BackgroundHiCache on sglang-torchtpu, and how vllm-torchtpu differs

Both stacks move KV between TPU HBM and host DRAM over tpu-sync (Raiden). They put the control of that movement in different places. This section describes the sglang-torchtpu design that Parts 1 to 5 build on, then sets it against the vllm-torchtpu design.

HiCache in sglang-torchtpu

HiCache is upstream SGLang's hierarchical KV cache. The radix tree keeps one entry per cached token run and records, for each node, where its KV lives: on the device (L1), in the host pool (L2), or in a storage backend (L3). The scheduler thread owns the tree. A cache controller moves pages between tiers on background threads and reports back through ack queues that the scheduler drains each step.

The TPU plugin replaces only the data plane, in sglang_tpu/:

  • raiden_transfer.py owns one Raiden KVCacheManager per rank over the fused device pool and the host pool. D2H and H2D are raw-buffer DMAs that return a pollable future. No device stream and no CUDA event exist on TPU, so the controller gates the whole forward on a batch event instead of per-layer events.
  • raiden_cache_controller.py overrides the three transfer-issuing methods of the upstream controller. Queues, ack draining and write policy stay upstream.
  • kv_pool_host.py is a page-granular host pool. Raiden owns the pinned memory; SGLang owns the free list. Plan B added quarantine() to it.
  • kv_free_fence.py and the hybrid controller hold a D2H until the forward that wrote the page has landed, because Raiden's D2H is not ordered against TPU compute.
  • Hybrid sliding-window models get one host pool per sub-pool with the raiden io backend. The torch_tpu io backend mirrors only the full-attention pool and rejects hybrid models.
  • Decode side: with --disaggregation-decode-enable-radix-cache and HiCache, the decode engine keeps finished requests in its tree and host pool. pd_decode_swa_hicache.py keeps only full-attention KV in RAM for sliding-window models and holds a request that reuses pages of an unfinished restore.

Two knobs matter for this work. --hicache-host-memory-mode cache keeps L2 as a resident tier; buffer_only turns it into pass-through staging for L3, which Plan B needed so that recalls had landing slots. --hicache-ratio sizes L2 as a multiple of L1.

How vllm-torchtpu does it

vllm-torchtpu has no host tier inside its scheduler's prefix cache. Host offload is a KV connector, TPURaidenOffloadingConnector, that subclasses vLLM's OffloadingConnector. The memory, the directory, the LRU, the pins and the DMA all live in tpu-sync's native KVCacheStore, which runs in the scheduler process. Workers register their device KV buffers once with the store's KVCacheManager and act as passive DMA endpoints for the store's save and load jobs.

  • Save fence. Each rank records a TPU event after the forward that wrote the blocks and acknowledges the job only when the event has retired. The scheduler launches the save after all ranks acknowledged. Same problem as the sglang D2H fence, solved per job instead of per batch.
  • Block reuse. When a device block is about to be reused, the scheduler cancels fence-pending stores and drains active transfers before it ships the step's metadata. sglang keeps the host reference on the tree node instead, so the page cannot be reused while a backup reads it.
  • Failure. A failed load reports its destination blocks and the request recomputes them. A failed save is retried once. Plan B copied both rules.
  • Granularity. One store entry per physical kernel block, with a logical vLLM block mapped to several entries by a size factor. Keys are coarse, in the thousand-token range. SGLang keys are 64-token pages.
  • P/D. A decode engine stacks the offload connector under the P/D transfer connector in a TPUMultiConnector, so the decode host's DRAM holds KV for the decode engine's own reuse. The prefill engine does not read it back.

vllm-torchtpu: how prefill KV reaches decode DRAM, and who reads it back

This is the same question Plan C answers for SGLang, asked of vllm-torchtpu. The short answer: the prefill's KV does land in decode DRAM, the decode engine reads it back for its own later requests, and any replica can read it through the global registry. The prefill engine itself never reads decode DRAM.

The four facts to remember.

  • Offload is per engine and unconditional. Each engine with the offloading connector saves every block it computes or receives into its own KVCacheStore, after a TPU-event fence confirms the forward wrote it. There is no decision to send a block to the other host for offload; the P/D pull is the only reason a block crosses the network.
  • Recall on the decode is a local load. At admission, the decode's offloading connector probes its store with the request's hash chain. A hit needs whole offload keys, bytes on the host (HOST or HOST_AND_HBM), no save or remote read in flight for that key, and the entry still in the LRU. Hits are loaded H2D into decode HBM; only the rest is pulled from the prefill.
  • Recall on the prefill is also a local load. The prefill's connector reads only the prefill's store. A prefix the prefill evicted is recomputed, which costs less on vLLM's critical path than on SGLang's, because the decode, not the prefill, matches the session's next turn.
  • Cross-host reads go through the registry, not through a peer relation. Stores publish keys with a TTL. A lookup walks the hash chain and, for each block, returns one owner by round robin over every store that holds it, filtering the caller out. The reader issues read_remote straight into HBM; nothing is pinned or cached locally for it. This serves replicas of the same role sharing prefixes; it would let a prefill read a decode's block only by coincidence of the round robin.

Against Plan C in one line each. Same spill: a by-product of the P/D transfer plus the decode's own offload. Different recall: vllm-torchtpu returns the block to the decode, Plan C returns it to the prefill. Different directory: a flat hash registry across the fleet versus the decode engine's radix tree, asked by the one prefill that feeds it.

vllm-torchtpu: what happens to one request, tier by tier

When a request reaches a vLLM engine's scheduler, its prompt is cut into blocks and each block gets a hash chained from the previous block's hash. Every tier is then asked, in a fixed order, for the longest leading run of those hashes it holds. The walk stops at the first tier that can answer, and only the tokens after that answer are computed. Three details that decide behavior. First, granularity: the store's unit is the offload key, a span of several kernel blocks, so a hit must cover the whole span; a request shorter than one span never hits the store. Second, pending state: a key whose save or remote read is in flight answers HIT_PENDING, and the scheduler re-asks on its next step instead of loading torn bytes; a key marked HBM with no live job is the residue of a failed save and counts as a miss, so no request waits on it forever. Third, ownership: in the multi-connector, whichever child reports a hit first owns the request's load, so on a decode the order of the children in the configuration decides whether its own DRAM or the prefill is preferred for an overlapping prefix.

What this looks like against Plan C. The SGLang prefill walks its radix tree once for HBM and host DRAM together, then asks one specific engine, its decode, by sending tokens, and receives the answer from that engine's tree. vllm-torchtpu walks a hash table, then a store, then a fleet-wide registry, and never asks a specific engine. Both stop at the first miss and compute the rest.

What a global registry buys, and what it does not

A registry turns a set of private host tiers into one addressable pool of KV copies. It does not move requests and it does not hold KV. It answers one question for a reader that has missed locally: for each block of my prefix, which store holds a copy, and what is its id there. The reader then fetches the bytes itself.

What it buys.

  • Reuse across replicas without session affinity. A router can send a session's turns wherever there is capacity; whichever replica computed the prefix last, its DRAM copy is reachable.
  • Shared prompts computed once per fleet. A system prompt, tool schema or retrieved document saved by one replica is found by all the others.
  • Warm starts. A replica that restarts or scales up has an empty cache but a full directory to read from.
  • One directory for any number of stores. Adding a replica adds a publisher and a reader; no replica needs to know the others.
  • Self-healing membership. Entries carry a TTL and stores report evictions, so a dead or full replica drops out of the answers by itself.

What it does not do.

  • It does not route requests. The engine that received the request keeps it. The registry only tells that engine where to copy blocks from. Choosing which engine should run a request is the router's job, and the registry does not talk to the router.
  • It does not see HBM. Only blocks saved to a host store are listed. A block that is in some engine's HBM but not yet saved is invisible.
  • It does not pick the nearest or the best copy. The choice is round robin per block over every owner. Two blocks of one prefix may come from two different hosts.
  • It does not keep a local copy for the reader. A remote read lands in HBM and leaves no entry in the reader's store, so the same miss repeats until the reader saves the block itself.

The code trail for "B fetches A's DRAM". On the vllm-torchtpu side, the scheduler-side manager in offload/raiden_store.py stashes the registry's answer as remote slices during lookup, and submit_load_job splits a load into local hashes, sent to store.load(), and remote hashes, sent to store.read_remote(remote_hashes, remote_slices, dst_device_ids). That call is tpu-sync's KVCacheStore.read_remote in api/torch/kv_cache_store.py: it returns as soon as the reads are issued, takes no pin, and routes each slice by status. Its native side, kv_cache_store.cc ReadRemote, groups the slices by owner and hands the peer group to host_offload_backend.cc, which does the four steps: ResolveStore(remote_id) through the registry client to get the owner's address; allocate free host staging blocks in B's own pool; call the owner's Fetch RPC with the hashes, B's staging block ids, B's Raiden id and B's DMA endpoints, so A's store DMAs from A's DRAM into B's staging over Raiden; then an H2D future copies the staging blocks into B's device blocks and frees the staging. A's engine is never involved; only A's store process answers.

So, can a block be routed to another engine to fetch the KV? The direction is the reverse of that sentence. The KV is fetched to the engine that holds the request, from whichever engine's DRAM the registry names. If what you want is to send the request to the engine that already has its KV in HBM, that is prefix-aware routing in the router, which a registry can inform but does not perform, and which neither stack does today. Plan C sits between the two: it fetches KV to the prefill like a registry read does, but from one named engine, the decode, without a directory.

Part 1Design

Problem and goal

In a 1P/1D deployment the prefill engine computes the KV cache of a long prompt and sends it to the decode engine. When the same user comes back, the prefix is often gone from the prefill engine: its HBM and its host DRAM tier are private and small. The engine then recomputes the prefix. At 128k tokens this costs 6 s, at 256k it costs 17 s, on each turn.

The goal is to keep an evicted prefix addressable in DRAM that the prefill engine does not own: the decode host's DRAM. The decode host lends memory through separate Raiden store processes. A later request finds the pages in a global registry and pulls them back over the native Raiden transport. The decode engine is not changed.

Architecture on the pair

Ownership and safety rules

  • One allocator for each memory. The prefill host slots belong to SGLang's TpuRaidenHostKVCache. The store processes own their DRAM.
  • The prefill side pins with references. HiCache holds the host reference during batch_set_v1. On the store side, Fetch pins the source during the full copy.
  • Quarantine, not reuse. When native DMA can still touch a slot, the backend retires the slot until the process restarts. A gRPC cancel is not a DMA cancel.
  • The namespace is the identity. The store group name is kv_pool_group.pool.sha256(material)[:24]. The material contains your cache_namespace, the model name, the TP/DP/PP ranks, the pool, the page size, and the shape and dtype of each layer. If you change the weights and keep the namespace, the engine serves old KV.
  • Manifests start the stores. Each rank and pool writes <manifest_dir>/<namespace>.json at attach time. launch_stores.py turns the manifests into store processes on the decode host.
  • Python moves identities, Raiden moves bytes. The wire subset is 6 RPCs and 62 fields, carried in a private protobuf package.

Spill path, one call at a time

  1. A page is cached on the prefill engine. After a prefill chunk, the radix tree inserts nodes. With write_through, the TPU HiRadix cache starts the D2H backup. The Raiden fence confirms the host copy. The cache then calls write_backup_storage, which puts a StorageOperation with the host indices and page hashes in the backup queue.
  2. The backup thread takes the operation. _page_backup processes it in batches of STORAGE_BATCH_SIZE = 128 pages and calls storage.batch_set_v1(hashes, host_indices). For hybrid SWA models the HybridCacheController calls batch_set_v2 with one PoolTransfer for each pool.
  3. The backend prepares the batch. _io(write=True) takes the backend lock. It changes the host indices into whole page ids. It rejects an index that is not aligned or a page that occurs twice. It hashes namespace ‖ key with SHA-256. It calls client.spill.
  4. The client finds the store. spill goes through the ordered replica list and asks the registry ResolveStore for each store's address.
  5. The client sends WriteRemote. The request has the source Raiden id, the hashes, the prefill host page ids and the prefill DMA endpoints. The store answers with an ack: ALL_EXIST (done), PARTIAL_EXIST (send the rest again), or an operation_id (admitted, pull in progress). Admission is never success.
  6. The client reads the result. COMMITTED and ALL_EXIST are success. STORED_UNREGISTERED is failure. FAILED and unknown states cause quarantine. If the stream breaks after admission, the client asks PollWriteRemote one time.
  7. The backend records the result. Quarantined batch indices become host pages given to pool.quarantine(). The boolean list returns to the controller, which stops at the first failed batch.

Recall path, one call at a time

  1. The scheduler asks the storage. When a prefix is not fully in L1 or L2, prefetch_from_storage gives a PrefetchOperation (uncached token ids, last local hash) to the controller's prefetch queue.
  2. The prefetch thread asks for hits. _storage_hit_query computes page hashes with get_storage_hash_str and calls storage.batch_exists in batches of 128 pages until the first miss. In the backend that is a registry Lookup. For SWA pools the v2 variant also probes a trailing window.
  3. The ranks agree. An all-reduce (MIN) across the TP ranks sets the hit count.
  4. The backend fetches into L2. With wait_complete, the scheduler allocates host slots for the hit pages. client.recall looks the hashes up again, groups them by owner store, resolves each owner and sends Fetch with the destination page ids. The store pins its source, copies into the prefill DRAM and returns done_block_hashes. The client accepts the batch only when the done set is equal to the request.
  5. HiCache loads into HBM. The existing H2D path runs. The forward gate waits for the Raiden events. The scheduler runs the request with the pages marked as cached (cached_tokens_details.storage).
  6. Failures. NOT_FOUND, INVALID_ARGUMENT, FAILED_PRECONDITION and UNIMPLEMENTED are clean misses; the request recomputes. A timeout or transport error quarantines the destination slots.

Four things come out of this function.

  1. The namespace. A SHA-256 over the material above. Every storage key is later hashed together with it. Two engines with a different rank, page size, dtype or layer shape can never hit each other's pages, even if they share a registry.
  2. The store group. The string that names the store for this rank and pool. The registry and the store processes use it as the kv_pool_group.
  3. The KV transfer spec. client.publish_spec(group, block_bytes) tells the registry the byte size of one page in each layer. A store that starts later with a different geometry is refused by the native code.
  4. The manifest. A JSON file named by the namespace in manifest_dir. It holds the group, the registry address, the decode job name, the replica list and the block bytes. The file is written to a temporary name and then renamed, so the launcher never reads a half file.

The descriptor comes from the transfer object that already owns the Raiden manager for this rank. It reads the layer shapes from metadata and exports the DMA endpoints of the existing host pool. No second allocator is created.

def host_store_descriptor(self) -> dict:

        if (start < 0 or start % size or start // size >= pool.page_num
                or values[offset : offset + size] != list(range(start, start + size))):
            raise ValueError("Raiden storage requires aligned contiguous host-page runs")
        pages.append(start // size)
    if len(set(pages)) != len(pages) or len(set(keys)) != len(keys):
        raise ValueError("Duplicate host pages or keys in a Raiden storage batch")
    return pages

The page check is strict on purpose. The Raiden host pool allocates whole pages, so each key must map to one page-aligned run of page_size token slots. A batch that breaks this rule is rejected before any RPC, and the controller sees a failed batch, not a wrong page.

3. The shared IO routine

Spill and recall share one routine. It holds the backend lock for the full call, which is the cause of Risk 1 in Part 4.

def _io(self, name, keys, indices, *, write):
    keys = list(keys)
    if not keys:
        return []
    with self._lock:
        state = self._state(name)
        pool = state["pool"]
        pages = self._pages(pool, keys, indices)
        hashes = self._hashes(state, keys)
        try:
            if write:
                result = self.client.spill(state["group"], state["targets"], state["source"], state["endpoints"], hashes, pages)
            else:
                result = self.client.recall(state["group"], state["source"], state["endpoints"], hashes, pages)
        except Exception:
            logger.exception("Raiden storage IO failed; retiring its host slots")
            result = IOResult(quarantine=frozenset(range(len(keys))))
        if result.quarantine:
            selected = torch.cat([indices[i * pool.page_size : (i + 1) * pool.page_size] for i in sorted(result.quarantine)])
            pool.quarantine(selected)
            self._stats["quarantined_pages"] += len(result.quarantine)
        self._stats["spill_pages" if write else "recall_pages"] += len(result.done)
        self._stats["failed_pages"] += len(keys) - len(result.done)
        return [i in result.done for i in range(len(keys))]

Three rules live here.

  • An unexpected exception is a quarantine, not a crash. The controller's IO worker thread must stay alive. The slots are retired because a peer may have borrowed them before the exception.
  • The result is a list of booleans in batch order. IOResult.done and IOResult.quarantine hold indices into the batch, not page ids. The controller stops at the first False.
  • Counters are updated under the lock. get_stats() reads them under the same lock, so a metrics scrape never sees a half update.

4. WriteRemote: admission is not success

The spill RPC is a server stream. The store first sends an ack, then pulls the pages from the prefill host, then sends a result. The client reads both events and maps them to one of three outcomes. The comment at the top of client.py states the rule: never treat admission as completion.

for event in call:
    kind = event.WhichOneof("event")
    if kind == "ack" and not acknowledged:
        acknowledged = True
        ack = event.ack
        if ack.exist_state == w.WRITE_ALL_EXIST:
            return IOResult(all_indices)                      # nothing to copy
        if ack.exist_state == w.WRITE_PARTIAL_EXIST:
            return IOResult(self._subset(hashes, ack.existing_hashes))   # caller re-offers the rest
        if ack.exist_state != w.WRITE_EXIST_STATE_UNSPECIFIED or not ack.operation_id:
            raise ValueError("Invalid WriteRemote admission")
        operation_id = ack.operation_id                       # admitted: the pull starts now
    elif kind == "result" and operation_id:
        return self._write_verdict(hashes, event.result)
    else:
        raise ValueError("WriteRemote events arrived out of order")

The verdict function maps the store's final state to the batch result.

Store stateMeaningClient outcome
COMMITTED, ALL_EXISTPages are in the store and registered.Success for the whole batch.
PARTIAL_EXISTSome pages were already there. The others were not copied.Success for the existing subset. spill offers the rest again, and stops when a round makes no progress.

If the stream breaks, the client separates two cases. A rejection before the ack, such as RESOURCE_EXHAUSTED when the store is full, means the store never touched the slots, so the batch is a clean failure. A break after the ack means the pull may be running. The client then asks PollWriteRemote one time with wait_ms=0. If that also fails, the slots are quarantined.

if operation_id:

            w.PollWriteRemoteRequest(operation_id=operation_id, wait_ms=0), timeout=self.timeout_s)

    except (grpc.RpcError, ValueError) as exc:

# a gRPC cancellation is not a native DMA cancellation.
return IOResult(quarantine=all_indices)

The request also sets deadline_ms to 80 percent of the RPC timeout. The store then stops its own work before the client's gRPC deadline, so the client usually sees a terminal result instead of a broken stream.

5. Fetch: the store writes into slots HiCache owns

The recall RPC is a plain unary call. The client sends the hashes and the destination page ids, plus the prefill rank's own Raiden identity and endpoints, so the store can address the prefill host pool.

Two details matter.

  • Owners are grouped. recall runs Lookup first and groups the hits by the Raiden id of the store that holds them. One Fetch goes to each owner. With one replica this is one call per batch.
  • A partial answer is a failure. The native Fetch returns after it has copied, so the client demands that the done set equals the request. Anything less raises, and the error path decides between a clean miss and a quarantine with the same status-code rule as the write path.

6. Lookup and the hybrid pools

The controller asks for a hit count, not a hit list. batch_exists returns the length of the longest prefix the registry knows. A registry error is a miss, never an exception, so a registry outage degrades to recompute.

def _hit_count(self, name, keys):
    state = self._state(name)
    try:
        return len(self.client.lookup(self._hashes(state, keys), state["source"]))
    except (grpc.RpcError, RuntimeError) as exc:
        logger.warning("Raiden storage lookup failed; treating as a miss: %s", exc)
        return 0

For hybrid sliding-window models the HybridCacheController calls batch_exists_v2. The KV pool sets the candidate prefix lengths. Each extra pool then narrows them. A pool with the TRAILING_PAGES policy only needs its last window of pages, so the code probes each page on its own, because the registry's prefix lookup stops at the first gap and would hide a complete later window.

7. Quarantine in the host pool

The host pool change is small and permanent. A quarantined page leaves the free list and never returns, not on free(), not on clear() after /flush_cache. Only a process restart makes the page usable again, because only then is it certain that no remote DMA still targets it.

def quarantine(self, indices: torch.Tensor) -> None:
    pages = set(self._to_page_ids(indices))
    if any(p < 0 or p >= self.page_num for p in pages):
        raise ValueError("Quarantined page is outside the host pool")
    with self.lock:
        self._quarantined_pages.update(pages)
        self.free_pages = deque(p for p in self.free_pages if p not in pages)

def free(self, indices: torch.Tensor) -> int:
    page_ids = torch.unique(indices.cpu() // self.page_size).tolist()
    with self.lock:
        reusable = [p for p in page_ids if p not in self._quarantined_pages]
        self.free_pages.extend(reusable)
    return len(reusable) * self.page_size

In the live runs no page was quarantined. The counter exists for the two cases the tests force: a stream that breaks after admission and a Fetch that times out.

10. How the code is tested

The CPU tests run without TPUs and without tpu-sync. A StoreFixture in the test file implements the registry and store services in Python on a local gRPC server, and the test attaches a real RaidenDramStorage to a real TpuRaidenHostKVCache whose transfer object is replaced by a fake. Each test then drives the backend through the same calls the controller makes.

  • Correctness. Spill, forget, recall into different slots; a new prefill instance recalls through the registry; owners are grouped and the destination order is kept; manifest and launcher produce a rank-specific store command.
  • Verdict rules. Admission ack does not finish a backup; a lost stream recovers a committed write; partial-existing offers retry only the missing keys; STORED_UNREGISTERED is not success; an uncertain write retires its slots across reset; a failed Fetch never admits data.
  • Fail closed. Wrong group never transfers; the namespace blocks incompatible hits; layout and dtype are part of the namespace; invalid or duplicate host indices are rejected before any RPC; an unexpected IO error quarantines; a bad lookup verdict is a miss before any transfer.
  • Hybrid. SWA recall with non-contiguous restorable boundaries.
  • Concurrency, five tests. Eight threads and a flusher for 10 s; a stalled WriteRemote holds a lookup for the timeout and not longer; a registry outage returns misses at once; close() during IO does not deadlock; KV and SWA pools from six threads at once.

The on-device test in test/manual/tpu/test_raiden_dram_spill_recall_ondevice.py runs the same spill, forget and recall sequence against a real native store on one host and compares the bytes in HBM before and after. It passed in 3.2 s after fix 2 in the next section.

Limits and risks

A decode-host store is append-only until restart. At tpu-sync 73499f1, WriteRemote allocates landing blocks locked (kv_cache_store_service.cc:697), a committed write keeps them (:936), and nothing calls LogicalBlockManager::Unlock. The host-store node has no sweep. After budget / page bytes pages (29.8k per rank at 16 GiB), each spill fails with RESOURCE_EXHAUSTED ... Evictable: 0 and sessions fall back to recompute. Size the budget for the session population, or restart the stores.
One lock holds lookups behind a spill in progress. _io and batch_exists share the backend lock, and _io holds it during the full gRPC call. A stalled store adds up to rpc_timeout_s (60 s here) to the TTFT of a request that needs a lookup. Seen live in W4. Lower the timeout, or take the lookup out from under the write lock.
cache host-memory mode starves recalls under churn. Use buffer_only with the store.
A registry restart loses the directory until the stores restart.
write_through spills each page. Every cached prefill page also goes to the decode host. The bundle does not port vLLM's low-watermark sweep. For long prefixes with few turns the cost is acceptable; for high-churn short traffic it is not.
Quarantine makes the prefill host pool smaller for the life of the process. The only signal is get_stats()["quarantined_pages"]; it is not a metric.
Only prefill-generated KV. Decode-generated tokens are never captured. A chat whose history contains the model's answers still re-prefills those answers.

What already exists in the tree

  • A decode-side prefix cache with host RAM. With --disaggregation-decode-enable-radix-cache and --enable-hierarchical-cache, the decode engine keeps the KV of finished requests in its radix tree, in HBM and in its host pool. DecodePrefixMatch in disaggregation/decode_hicache_mixin.py matches a new request against L1, L2 and even L3, and restores host pages to HBM before the pull. sglang_tpu/pd_decode_swa_hicache.py adds the TPU specifics: only full-attention KV goes to RAM, a request that reuses pages of an unfinished restore waits for it.
  • A consumer-pull transfer with a producer lease. RaidenKVManager in sglang_tpu/disaggregation/raiden/conn.py runs the P to D transfer as a pull: the producer calls register_read(req_id, uuid, block_ids) and holds a lease on those pages until poll_stats reports the read settled; the consumer calls start_read(req_id, uuid, endpoint, remote_block_ids, local_block_ids). Raiden stages the pages D2H on the producer, moves them over the network, and lands them H2D on the consumer. The sender and receiver halves are mixins on one class.
  • A control channel per rank. ZMQ sockets carry typed messages between the two managers: PULL_REQ, BLOCKS, CHUNK, ABORT and the reshard family (serde.py). A new message is one tag and one handler.
  • A prefill-side hook for a prefix that is not local. managers/scheduler.py computes the matched length from L1 and L2 and calls prefetch_from_storage for the rest. Plan C replaces this call with a peer fetch.
  • Inserting transferred pages into a radix tree. The decode engine already does it for pages it pulled from the prefill. The prefill engine will do the same for pages it pulled from the decode.

In the recipes used for Parts 3 and 4, the decode engine runs with no radix cache and no HiCache. Plan C starts by turning these on. That is a configuration change, not code.

Why the duplicate is not avoided. Each engine keeps its own copy and evicts it on its own schedule. Removing the duplicate would need one of three things: a host to host copy at eviction time, which is Plan B's transport and what the reviewer's pattern excludes; a directory shared by both engines, which upstream HiCache does not have outside an L3 backend; or a two-phase eviction protocol so a page is never dropped on both sides at once. The duplicate costs DRAM in proportion to the working set, about 9.4 GiB per 128k context per host here, and no coordination. When decode DRAM becomes scarce, for example one decode host behind several prefill engines, this trade stops being right and the overflow needs a shared directory or a store-backed tier.

Two consequences follow. First, keep prefill L2 in cache mode at ratio 2. Its hits are two to three times cheaper than a remote recall, the DRAM is local and otherwise idle, and Plan C no longer needs the buffer_only trick, because the recall lands in HBM and needs no host landing slots. Second, size decode DRAM for the whole session population, not for the overflow. A page lives in both DRAMs at the same time, so the decode host pool must hold every prefix that may come back, at about 9 KiB per token per rank.

Recall, one step at a time

  1. The prefill scheduler finds a gap. For a new request, L1 and L2 match matched_len tokens. Today the scheduler calls prefetch_from_storage for the rest. In Plan C it calls prefetch_from_peer on the TPU HiRadixCache with the same arguments: the last local node, the unmatched tokens, the last hash and the salt.
  2. The prefill asks the decode. Each rank's RaidenKVManager sends PREFIX_REQ to its peer rank: a room id, the page hash chain of the unmatched tokens, and a deadline. One message per rank, because each rank holds its own KV shard.
  3. The decode matches and pins. The decode manager hands the hashes to the scheduler thread (the same queue that handles pull requests). The scheduler matches them in its radix tree, as DecodePrefixMatch does, and locks the nodes with inc_lock_ref. Pages that live only in the host pool are restored to HBM through the existing _try_hicache_queue_load_back path. Pages that are in neither tier end the hit at that point. The reply waits for the restore to land.
  4. The decode registers and replies. With the pages in HBM, the manager calls register_read(req_id, uuid, device_block_ids) and sends PREFIX_BLOCKS with the hit length, the block ids and its Raiden endpoint. The lease on the pages starts here and ends when the read settles, as in the forward direction.
  5. The prefill pulls. The prefill manager allocates device pages from its own allocator for the hit length and calls start_read. The pages go D2H on b, over the network, and H2D on a. The scheduler polls poll_stats as it does for the forward direction. On a miss or a failure, the request keeps matched_len and recomputes the rest, with no other change.
  6. The prefill inserts and runs. When the read settles, the prefill scheduler inserts the pulled pages into its radix tree under the request's tokens, re-matches, and schedules the request with the longer prefix. Only the new tokens are prefilled. The prefill sends PREFIX_RELEASE; the decode unlocks the nodes.
  7. Spill of the new pages. After the prefill, the request goes to the decode through the normal P to D pull. The decode's HiCache writes through to its host pool. The next turn finds the longer prefix on the decode side. The prefill's own HiCache host pool keeps its usual role and needs no storage backend.

Trade-offs against Plan B

No new processes and no second allocator. One HiCache per host owns its memory. Eviction exists from day one, because the decode host pool has an LRU. Plan B's append-only store limit goes away.
KV produced by decode is reusable too. The decode tree holds the answer tokens' KV. The next turn's prefix includes the previous answer, so the recall covers it. Plan B only spills prefill-generated KV.
Matches how HiCache is meant to be used. The pattern is the one the reviewer asked for, which lowers the review cost upstream.
The decode scheduler is on the recall path. Match, lock and restore run on the decode scheduler thread between decode steps. At 8 ranks and a 128k prefix that is 2,048 pages per rank to restore and register. The decode step cadence sets a floor on recall latency that Plan B's separate processes did not have. Mitigation: handle PREFIX_REQ on the listener thread with a tree lock, restore in the background, and reply from the event callback.
The decode HBM is shared. A restore from the decode host pool needs free decode HBM pages before the prefill can pull. Under heavy decode load the restore waits. Raiden's producer reads device pages only; serving straight from the decode host pool would need a tpu-sync change, a host-source register_read, which would also remove one copy.
Two hops per recall instead of one. Plan B: decode-host DRAM to prefill host DRAM. Plan C: decode host DRAM to decode HBM, then decode HBM to prefill HBM through two staging buffers. Expect a recall to cost more than Plan B's 2.6 s at 128k unless the pages are still in decode HBM.
One decode engine per prefill lookup. With several decode engines, the prefill must ask the one that served the previous turn, or all of them. The router already pins a session to a decode engine in most deployments; the fetch should use the same key.

A transport finding, not a feature defect. The client-abort phase drops the connection 0.5 s into a recall. Before the pull that abort landed while the prefill was still computing and was cleaned up at once. With the pull the recall is ready in under half a second, so the same abort now lands while the prefill-to-decode transfer is in flight. The decode fails and drops the room; the Raiden sender on the prefill marks its side aborted but, by design, keeps the inflight entry until the transfer's DMA lease settles, which with the peer gone is its own timeout of 600 s. The prefill is not idle for those ten minutes and every deferred cache flush in that window fails, which is what took the four phases after the abort down. The stress run now aborts a fresh prompt during compute early (that must flush cleanly) and keeps the transfer-time abort as its last phase, and the behaviour is noted for the Raiden owners.

Procedure used here

CAUTION: Do not commit the patched checkout to sglang-torchtpu. Keep it as an uncommitted worktree. Put code changes and results in tpu-rl.
  1. Make sure that no other user holds the TPU on either host: bash ~/pd_disagg/scripts/tpu_free.sh.
  2. Use the patched checkout on both hosts: ~/sglang-spill.
  3. On the decode host b, start the registry: ~/pd_disagg/spill/spill_stores.sh registry-start.
  4. Start the pair from the patched tree: ~/pd_disagg/spill/pd_spill.sh start ~/pd_disagg/recipes/gpt-oss_C_spill_dram_bo.json <run>.
  5. When the prefill engine has written its manifests, start the stores on b: ~/pd_disagg/spill/spill_stores.sh stores-start <run> 17179869184. Make sure that 16 store processes are registered: spill_stores.sh status.
  6. Single turn: spill_bench.py --prefix 131072 --new 8192 --scenario flush --label recall --spill-wait 120. Agentic: spill_agentic.py --sessions 8 --turns 6 --prefix 131072 --turn-new 4096 --turn-out 512. Stress: spill_stress.py.
  7. Restart the stores between workloads so the append-only budget does not fill.
