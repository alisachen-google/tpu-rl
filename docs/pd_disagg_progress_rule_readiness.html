Progress-Rule Readiness

The simplest readiness rule that unblocks #1276: an engine is unhealthy when it has had demand for a whole window and produced nothing in it. One rule for prefill and decode, no peers, no state machine. Two implementations are open side by side, both as single commits on main: both are now TPU-plugin only, installed through the plugin's patches.py: #1390 judges in each scheduler rank and publishes to a slot file in /dev/shm, with a staleness rule for a hung loop; #1392 judges in the HTTP process from its own request bookkeeping and hands an idle engine to the core probe. This page shows the rule, both data flows, the hang case, and what the live runs found.

UNHEALTHY ⇔ demand continuously for T and nothing produced for T

Demand is a real request held anywhere on the engine's P/D path, or one the engine itself concluded without output within the window (handshake failure, transfer failure, transport timeout). Produced is a generated token on a decode, or KV released after a completed transfer on a prefill. Probe requests and client cancels count for neither. Until the first thing an engine produces after start, the window is T_cold. Recovery needs no state: when the held requests leave and the last failure ages out, demand is gone and the engine is ready; the next request gets a fresh window.

2. Scheduler-side snapshot: how the facts reach the probe

This is what PR #1390 implements. The scheduler owns the facts, judges them on every loop iteration, and copies the verdict into the shared-memory load snapshot. The HTTP process reads that copy when a probe arrives and never calls into the scheduler.

3. The blind spot, and the two ways to close it

If the scheduler loop hangs while requests are pending, the loop that counts them, judges them and writes the snapshot is the loop that hung. The snapshot keeps the last verdict, ready, and the probe reports it faithfully. Today the fall-through one-token probe catches this by timing out. If the probe is removed, something else must.

6b. Per-peer rule on the decode (PR #1393, stacked on #1392)

The router stamps the prefill's bootstrap host and port on every decode request, so the decode's HTTP process can attribute each outcome to a peer. A peer is failing after SGLANG_TPU_PD_HEALTH_PEER_FAILURE_STREAK (3) consecutive aborts with no success in between, the last inside the window, or when its requests have been in flight for a window with nothing back. The decode is unhealthy once failing peers reach SGLANG_TPU_PD_HEALTH_PEER_FAILURE_RATIO (50%) of the peers active within the window, with at least SGLANG_TPU_PD_HEALTH_PEER_MIN (1) active. The engine-wide rule stays and the two are ORed; the 503 body carries both records. Prefills keep the engine-wide rule only: their requests do not name the decode they pair with.

Live, 2P/2D with one prefill's sender broken: the decode on the branch answered 503 with peers failing: 1 of 2 active ... 10.128.15.217:8998 while its engine-wide rule stayed ready and the decode on main stayed 200. The verdict cleared between bursts because the broken prefill reports 503 itself, the router pulls it from the pool, and the decode then has nothing outstanding to it: the same stateless recovery as the engine rule, working end to end. A first pass found that requests which never abort left a peer unjudged; fixed, with a test.

6c. Trade-offs: HTTP side against scheduler side

Both designs catch the issue 1276 failure and a scheduler that hangs while holding requests. They differ in what else each can see, how much it takes to operate, and where each is the only option.

Only the scheduler side can

  • Run without a Python HTTP process. With SGLANG_RUST_SERVER the Rust server hosts the API, tokenizer and detokenizer inside the scheduler process; the TokenizerManager never runs, so there is nothing for #1392 to wrap and its /health is static 200 from the moment the port binds.
  • Judge a long prefill without a false 503. The scheduler sees each chunk complete and each transfer poll advance; the HTTP process sees nothing until the final output, so a single prompt longer than T looks like a stall.
  • Name the cause and the rank. "KV pool full, preallocation failing" against "transfers never complete" against "rank 5 stuck" are facts only the scheduler holds.
  • Flag degradation before requests fail. Transfer latency, handshake retries and bandwidth live in the KV poll states; the HTTP side only sees end-to-end outcomes.
  • Act locally. Stop accepting bootstraps, abort stuck requests early, or report through the load snapshot the router already reads.

Only the HTTP side can

  • See a dead detokenizer or a broken scheduler-to-HTTP link. The scheduler's verdict stays ready and its slot stays fresh, because from where it stands tokens were produced. Only the process waiting for the output notices it never arrives.
  • Give a verdict that cannot be stale. No slot file, no republish timer, no dead-pid handling, no staleness rule: the facts are read in the same process that answers.

How to read it

The HTTP side wins on simplicity and on the one failure between scheduler and client that the scheduler cannot see. The scheduler side wins on richness of evidence and on deployments without the Python HTTP layer. If the Rust server becomes the production front end, or chunk-level prefill progress and per-rank reasons become requirements, #1390's plumbing is built and validated for them. The two combine cleanly: the HTTP-side verdict as the readiness answer, the scheduler-side slot as the source of reasons and compute-level progress.

7. Recommendation

Ship the rule; move the clock. The rule is right: it reproduced every expected verdict on both roles and its one gap was a bookkeeping gap, now closed. The scheduler-side snapshot is a correct implementation of it, but it is the scheduler describing itself, so it needs either the one-token probe or the staleness rule to cover a scheduler that stops. The HTTP-side variant evaluates the same three numbers in the process that answers the probe, is live by construction, covers a hung detokenizer as well, needs no shared memory, sends no probe while loaded, and is less code. The live scenarios are the same for both, so the switch costs a rewrite of the plumbing, not of the validation.
