Pathways × vLLM TPU inference

Many DP lanes.
One synchronous doorway.

How DPScheduler turns independent request schedulers into one rank-major JAX program—and why the Gemma4-E2B G4R7B rollout migrates from a TPU collective roof to a serialized host/control-plane roof.

Bottom line: TP=1 was still the right measured mesh choice: removing tensor-parallel collectives cut rollout time. But Pathways forbids vLLM-native multiprocess DP, so every logical lane still converges through one parent, one JAX proxy client, one global SPMD launch, one blocking host materialization, and one output scatter. At high DP, that serial boundary becomes the next roof.

01 · End-to-end mechanism

One decode window through DPScheduler and Pathways

The scheduler children are real OS processes, but they are CPU-only control-plane helpers. A DP rank is a logical JAX mesh lane—not an independent Pathways client, TPU server, or model engine. Select a numbered stage in the SVG.

01

Admission is local—and expensive at high DP

For each new request, stock routing asks every rank about prefix hits, pending prefill, in-flight count, and minimum remaining output. The winning rank becomes sticky because KV and prefix state are rank-local. Batch-prefill buffering currently drains by routing requests one at a time.

02 · What our case actually looks like

G4R7B: 128 job devices, 64 rollout lanes

The GCS log is the source of truth for scheduler topology. The report’s “DP128” shorthand counted the whole allocation, including the training half. For scheduler analysis, that distinction changes every O(DP) estimate by 2×.

2048 completions ÷ 64 DP lanes = 32 completions/lane = 4 prompt groups × 8 sibling generations
up to 64

decode windows

With a 64-token continue-decode window and a 4,096-token cap, a cap-length completion can traverse 64 global scheduler/JAX boundaries. Shorter and finished requests take fewer.

131,072

token slots/window

At full occupancy, a fixed output buffer can contain 2,048 requests × 64 token steps before trimming and conversion to Python structures.

all 64

must rendezvous

Every global window fans scheduling out to all logical ranks and waits for all outputs before the next combined JAX execution.

1,404 → 2,048

active-to-padded decode snapshot

Batch 17 had 1,404 active requests but executed a 2,048-row bucket: 68.55% occupancy and 644 padding rows. That is ≈21.94 active requests per lane versus the initial 32.

16,384

configured global request capacity

max_num_seqs=256 is per rank, so current code derives max_num_reqs=64×256. This is capacity/metadata headroom—not proof that every decode result has 16,384 rows—and should be right-sized in an isolated A/B.

Host-window anatomy

“Host-bound” means serial and synchronization-bound

These are inclusive mean spans from seven host steps in the profiled outer step 0. They overlap and must not be added. The 15.99 ms device interval comes from XProf without a shared host correlation ID, so the ratio is a coverage proxy—not a utilization counter.

The red bar is not removable CPU time. jax.device_get includes Pathways queueing, waiting for global completion, remote shard lookup, transfer, and host materialization. The actionable observation is that this wait is on a single dependency chain; more idle CPU cores do not help unless work or submissions can overlap safely.
Measured

Per profiled host step: 130 HostBufferStore::Lookup events, ≈772 StoreAsync events, and ≈232 DPScheduler _send_command spans. The log also has four 0.89–1.40 s schedule waits and 335 cold/early long-update warnings; one slow lane can stall the rendezvous.

Corroborated

Follow-up G4R8B used only 0.9–2.1 of 44 head cores during rollout. Doubling the CD window 64→128 halved boundary count but regressed rollout 96.7→99.5 s.

Interpretation

The roof is not simply “too many dispatch calls.” It is total serial work and waiting around each boundary: admission, Pipes, rank packing, proxy fan-in, extraction, and scatter.

At TP1, useful device work per lane becomes cheap while most terms above remain on one parent and several grow with D. The TPU is busy inside a short launched program; the global system then waits at the host/proxy boundary before it can launch again.

04 · Improvement plan

Attack the serial doorway in isolated A/Bs

The later G4R9P1 bundle reached clean engine samples of 64–67 s versus G4R7B’s ≈96.7 s, proving host-path headroom. It is not adoptable as evidence for any single change: it bundled routing, extraction, detokenization, cache/sync, and verifier changes, developed severe tails, and shifted the output contract. The next ladder must change one mechanism at a time.

0
Correlate and version-pin
Stamp exact tpu-inference/vLLM/JAX commits. Add stable IDs and timers around batch admission, rank probes, schedule/merge, input prep, proxy submit, completion wait, shard lookup bytes, extraction, split/update, detokenize, and full artifact cadence. Capture CPU samples after ≥5 warm steps.
Gate
DP 8/16/32/64 scaling curve; no profiler-cold extrapolation.
1
Group-aware batched admission
Assign each prompt’s eight sibling generations to one sticky rank; stripe the 256 prompt groups evenly (four groups/rank at DP64). Snapshot rank load once, route the batch centrally, and add an ADD_REQUESTS bulk Pipe command. This changes routing from O(R×D) probes toward O(R+D) without sacrificing prefix locality.
High priority
Same prefix-hit rate, prompt grouping, lengths, RNG, and reward.
2
Vectorize output extraction
Replace one np.isin per request with a matrix first-EOS pass, then vectorize host length/state updates. Implement adapter-compatible batched SentencePiece detokenization instead of a fallback loop. The profiled host trace attributes ≈66.95 ms/window to 9,707 extraction calls across seven windows.
Low risk
Byte-identical token IDs, EOS inclusion, texts, and finish reasons.
3
Right-size metadata + compact IPC
First A/B max_num_seqs=40, then 48, at DP64: today the block-table view is ≈16.5 MiB per KV group and current code zero-fills/re-packs the max-sized view each window. Then send packed arrays/deltas instead of D nested ModelRunnerOutput graphs, fast-return unused grammar broadcasts, shadow unfinished counts in the parent, and consider shared memory. The trace sees ≈12.54 ms schedule + 31.76 ms update spans/window.
Medium risk
Identical KV allocations, finish order, stats, and prefix state.
4
Make Pathways output host-friendly
A/B device-side reorder/compaction and a coarser output sharding before device_get. Returning lengths plus packed tokens, or gathering the small token result into fewer proxy buffers, may trade a small on-device collective for fewer host lookups. Measure lookup count, bytes, queue time, and transfer separately.
Measure first
130 lookups/window is suggestive, not yet causally mapped to 2×DP.
5
Repair overlap semantics
The code has an async copy/deferred collection path, but G4R8 changed the sampling/length distribution and was void. First make sync and async RNG/state transitions replay-exact; then test whether copy/materialization can overlap useful work or multiple device-side windows without host-visible intermediate state.
Currently blocked
No throughput claim until token stream and LENDIST are equivalent.
6
Parallelize the parent, then shard it
First prototype a process pool for pure host-side output extraction with explicit state-delta ownership. Then test 4–8 coordinator partitions or multiple heads, each owning a disjoint submesh and request groups. This is not simply enabling TPU_MULTIPROCESS_DP: Pathways explicitly rejects that mode, so client lifetime, compilation, weight/KV ownership, and failure semantics need a deliberate design.
High risk
Scale proxy clients gradually; verify no compile or HBM multiplication.
7
Then tune device work
Inside the captured active interval, XProf is HBM-side: 15.71 FLOP/B, 17.76 TFLOP/s, ≈30.7% of the modeled same-intensity HBM roof. Later targets include removing the unused scalar EOS all-reduce when EOS checking is disabled and optimizing two full-vocabulary sampling reductions—but only after host coverage rises.
Later
Current narrow kernel target projects sub-1% cadence impact under the 2.07% proxy.

Do not infer

  • “545 ms device_get = 545 ms CPU.” It includes remote queue/wait/materialization.
  • “2.07% coverage = 2.07% TPU utilization.” XProf reports ≈99% duty inside its active interval.
  • “Just set CD=128.” The controlled run was neutral/slower.
  • “Just enable async.” G4R8 changed the generated-token contract.
  • “Plain round robin is safe.” It can scatter eight siblings and destroy within-prompt prefix reuse.

End-to-end work outside DPScheduler

  • Reward tails reached 27–36 s on four warm steps; add verifier timeouts and smooth RPC/pool fallback separately.
  • Weight synchronization costs ≈10.38 s mean; instrument bytes, then A/B JIT/unroll and overlap/incremental options.
  • Artifact cadence adds ≈8.93 s beyond logged iteration; pipeline dequeue/report/upload.
  • Use full cadence and useful output tokens/s as adoption metrics, not only PHASETIME median.
